# ProblemSolving Lab v1.1.0 — Implementation plan

**Date:** 25 November 2026 · **Branch:** `feature/v1.1-quality-enhancements` · **Baseline:** `main` at `9c5010d` (v1.0.0)

This plan covers the full v1.1 brief (“Quality, Reliability & Methodology Enhancement”, parts 1–11). An earlier pass on this branch (commit `84a582f`, PR #1) already delivered part of this scope. Section 1 audits both `main` and that commit against the full brief; the remaining sections plan the work still to do.

## 1. Audit findings

### 1.1 `main` (v1.0.0)

| Area | Finding |
|------|---------|
| Save queue (`src/store/projects.ts`) | `drain()` copies the pending snapshots and **clears the queue before writing**. If `db.save()` rejects, the error is logged and the state set to `error`, but the snapshot is not re-queued. No retry. `flush()` returns `void` and resolves even after a failure. |
| Deletion | `remove()` deletes from IndexedDB without waiting for an in-flight write of the same project, so that write can recreate the deleted project. |
| Import | `put()` result is not checked; the toast reports success even if storage failed. |
| Lifecycle | `beforeunload` warning while saving; best-effort flush on `pagehide`/hidden. There is no recovery path if a write is lost. |
| Synthesis completion | A finding counts as complete if it links to *any* analysis or evidence, including an untested or inconclusive analysis. Evidence type and quality ratings do not affect completion. |
| Recommendation completion | “Traceable” only checks that a finding id is linked. A finding with no evidence (a broken chain) still counts. |
| States | Each step is complete or not; there is no way to express documented limitations or missing evidence. |
| Structure review | Four MECE questions. There is no causal-logic check (symptom / root cause / contributing factor / consequence), no tree-type check, and nowhere to record overlaps, gaps, corrections or reviewer comments. |
| Synthesis coaching | One form, with no distinction between data, finding, insight, implication, so-what and decision relevance. |
| Report | 11 sections that mirror the forms. Evidence classes appear per analysis, but there is no evidence register, no reasoning chain per recommendation, and no separate evidence-quality section. |
| CI | Tests and build run on push to `main`, but pull requests never run the production build. There is no lint step, and failure artifacts are kept for 7 days. |

### 1.2 Branch commit `84a582f` (first v1.1 pass) — what it already resolved

- Four completion states; finding support (validated / provisional / not linked); recommendation chains (backed / limited / precautionary / unsupported); justified precautionary actions.
- Six-question guided structure review with automatic observations and branch roles (driver / symptom / consequence).
- Synthesis ladder (data → finding → insight → implication → so what).
- CI split into quality and e2e jobs on PRs, with deploy only from `main`.
- Schema v2 and v1→v2 migration. Tests: 55 unit, 26 e2e.

## 4. Proposed changes

### 4.1 Priority 0 — data integrity
- **Recovery journal** (`src/lib/journal.ts`). Snapshots that are not yet persisted are written synchronously to `localStorage`. This happens when a write fails, and when the tab is hidden or unloading with pending changes. On startup, a journal entry newer than its stored project (by `updatedAt`) is **restored and re-queued**, and the user is told which projects were recovered. Entries are removed once the same or a newer version is persisted. Continuous persistence remains the primary mechanism; the journal is a recovery net, not a guarantee.
- **Save states** as the brief names them: Saving… · Saved · Unsaved changes · Save failed (retrying) · Retry required. The indicator shows the number of unsaved projects.
- `flush()` concurrency: each call waits until the queue is idle, or has failed for the edits that existed when it was called.

### 4.2 Priority 1 — evidence-based methodology
- **Finding classification:** verified · partially supported · preliminary · inconclusive · unsupported. Each comes with the reasons for it and **per-dimension quality checks** (reliability, accuracy, completeness, recency, confidence, methodological limitations).
- Synthesis criteria add **interpretation** (insight) to statement, links and implication. Uncertainty is required whenever a finding is not verified; it becomes a documented limitation, not a rejection.
- **Recommendation states:** evidence-backed · partially supported · precautionary · requires further investigation · unsupported. Each shows the reason, the **issues addressed** (derived via finding → analysis → issue) and the **limitations** that affect it.

### 4.3 Priority 2 — MECE review
- Review notes: identified overlaps, missing branches, required corrections, reviewer, reviewer comments.
- Roles: component/driver, **root cause**, **contributing factor**, symptom, consequence.
- An issue-tree vs hypothesis-tree comparison with examples.

### 4.4 Priority 3 — synthesis thinking
- New rung **6 · Decision relevance** and a field for **“what we initially believed that the evidence changed”**.
- A guided worksheet with the seven coaching questions.
- The draft sentence uses “Because [insight], [implication].” (EN) / «لأنّ [الاستنتاج]، فإنّ [الأثر].» (AR), assembled only from the user's own words. It is a coaching aid, not a mandatory template.

### 4.5 Report (part 7)
Thirteen sections:
1. Executive summary
2. Problem statement
3. Scope and constraints
4. Issue tree
5. Prioritization matrix
6. Work plan
7. Analysis results (hypotheses and test results)
8. Evidence quality and limitations (evidence register by class, quality ratings)
9. Key insights (verified conclusions separated from other findings)
10. Implications
11. Recommendations (with the reasoning chain)
12. Implementation plan
13. Risks and outstanding questions

The report adds a legend for the evidence classes and introduces no figures that the user did not enter.

### 4.6 UX (part 8)
Small labels distinguish **data entry**, **analytical validation**, **methodological review** and **completion status** on the relevant panels. Existing colours stay; there is no redesign.

### 4.7 CI (part 6)
Keep `npm run lint` (oxlint) and document why ESLint is not added. Keep PR checks (lint, typecheck, unit, build, e2e), deploy only after they pass, and keep failure artifacts.

### 4.8 Tests (parts 2E, 9)
- Unit: journal (write, restore-if-newer, ignore-if-stale, storage throwing); concurrent flush; flush during an active write; edits during flush; a store-level integration test reproducing D1.
- e2e: reload after a simulated failed write recovers the edit (D7); save indicator states; the 17-step journey in one project.

## 6. Test strategy

1. **Reproduce first.** Each confirmed defect gets a failing test (or documented reproduction on `main`) before the fix, then stays as a regression test.
2. **Unit tests** (Vitest) cover the pure logic: save queue, journal, lifecycle, evidence classification, completion states, migration, structure observations.
3. **Acceptance tests** (Playwright, production build under the Pages base path). Storage faults are injected by overriding `IDBObjectStore.prototype.put`. They cover the full 17-step journey, both languages, offline, and responsive layouts.
4. No existing test is removed. Assertions change only where the specified behaviour changed (e.g. section count, state names), and each change is listed in `docs/TESTING.md`.
5. Final gate: `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:e2e`, `npm run build`, then the same checks in CI on the PR.

## 7. Risks and backward compatibility

| Risk | Mitigation |
|------|-----------|
| Schema change | Version 2 has **not been released** (it exists only on this unmerged branch), so the new v2 fields extend v2 without a v3. v1 data (`main`) migrates to v2 with defaults; an accepted v1 review stays accepted. Covered by unit and e2e migration tests. |
| Journal restoring the wrong version | Only restore when the journal entry is strictly newer (`updatedAt`) than the stored project; sanitize like an import; tell the user what was recovered. |
| `localStorage` quota (~5 MB) | Journal writes are wrapped. If the journal fails, the existing banner, *Retry now*, *Export backup* and leave warning still apply. Documented as a limitation. |
| Stricter evidence rules | Never block legitimate uncertain findings: documented uncertainty → *complete with documented limitations*. Every warning states its reason. |
| Report length | Sections stay concise. Empty sections say “Not yet completed” rather than inventing content. |
| Main branch | No direct changes to `main`. All work stays on the feature branch and PR #1; nothing is merged automatically. |
